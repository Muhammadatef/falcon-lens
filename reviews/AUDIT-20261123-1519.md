# AUDIT 2026-11-23 15:19 GST: what must change for Falcon Lens to be a robust solution

Auditor: owner-commissioned (`.claude/agents/auditor.md`). Code audited: `origin/main` at `79163c1`. Live system audited: the main `falcon` stack at `https://localhost:8443`, read only (HTTP GETs, checks of Falcon Demo Bank `.test` fixtures and invented messages, Prometheus queries, `docker inspect` and `docker logs`). Nothing on that stack was restarted or changed.

Every statement below was measured in this audit unless it is marked **unverified**.

## Short answer

The URL path is sound and honest: the cascade, the deterministic arbiter, the edge security and the truthfulness of the published numbers all held up. Four things stand between this and a robust submission:

1. **The demo stack is not in a demo-ready state right now.** The Sentinel has been restart-looping and scenario 6 does not open its page. Both are stack state, not code on `main`, and both need the owner.
2. **Real websites get warnings too often**, and almost all of it is one cause: when the page cannot be opened, the verdict becomes "suspicious".
3. **A scam message with no link is rated "No warning signs found".** Message detection depends almost entirely on the link.
4. **Nothing told anyone about item 1.** No alert covers a dead service, and `make demo` reports a dead Sentinel as "skipped" and exits 0.

## Findings

### P0: blocks a working or truthful demo

**F1. The Sentinel on the demo stack is restart-looping.**
- Evidence: `docker ps` → `falcon-sentinel-1 Restarting (3)`; `RestartCount` 90; still restarting at 15:19. Prometheus `up{instance="sentinel:8000"}` = 0. Log: `HTTPStatusError 501 Not Implemented` from `http://host.docker.internal:11434/v1/chat/completions` in `falcon_sentinel/llm.py:155`, raised through `main.py:172 lifespan` → "Application startup failed".
- Cause: the container was created 13:39 GST, before the #64 commits of 13:54 and 14:00. The old image asks Ollama for `response_format`, which `inkling-2-mini-chat` does not support (`{"error":"structured output is unavailable"}`, reproduced with one direct call). A stuck incident is resumed at startup, the call fails, and the old code lets that kill the service. `main` has the fix (router, no `response_format`, `try/except` around `resume_unfinished`).
- Impact: no incidents, empty incident board, the Sentinel scene of the demo cannot run.
- Fix and owner: **owner/L1**, on the main stack: `docker compose up -d --build sentinel` from `main`, then `make demo`. I did not verify that a rebuilt Sentinel starts cleanly on this stack, because I may not touch it.

**F2. Demo scenario 6 (injected page) does not open its page on the demo stack.**
- Evidence: `POST /v1/check/url` for `http://falcon-demo-bank-injection.test/` → `suspicious`, `tier_reached: T1`, `degraded_reasons: ["not_rendered:internal_name"]`, no injection evidence. `docs/DEMO.md` expects the same verdict as scenario 2 with an instruction-like-text item.
- Cause: `FL_SSRF_ALLOW_HOSTS` in `falcon-worker-1` and `FL_EGRESS_ALLOW_HOSTS` in `falcon-egress-proxy-1` list 4 hosts. `.env.example` and the compose default list 7. Missing: `falcon-demo-bank-cloak.test`, `falcon-demo-bank-injection.test`, `falcon-bot-relay.test`. The main `.env` overrides the default with an older line. A fresh clone is not affected.
- Fix and owner: **owner**: copy the `FL_SSRF_ALLOW_HOSTS` line from `.env.example` into `.env`, then `docker compose up -d worker sandbox egress-proxy`. PR #78 makes the runner say this.
- Scenarios 2 and 5 pass live (`dangerous` 100 with H1 and H4 at T2 in 4.4 s; `no_warning_signs` with H3). Scenario 3 passes (`dangerous`, H5).

**F3. A scam message without a link is rated "No warning signs found".**
- Evidence, live, invented messages naming only Falcon Demo Bank:
  - "‹bank›: your card is stopped. Call ‹number› and send the verification code and ID number now" (Arabic) → `no_warning_signs`, 38.
  - The same ask in Arabizi → `no_warning_signs`, 15.
  - "You won AED 50,000 … reply with your card number, expiry and the OTP" → `no_warning_signs`, 38.
  - Arabic prize message asking for card number and PIN → `no_warning_signs`, 27.
- Cause: (a) H6 accepted only an explicit identity claim, not a bank named in the sender line, although `docs/SCORING.md` says "authority/bank impersonation"; (b) each message rule is worth 0.6 and about 2.1 is needed to reach `suspicious`; (c) the extractor's reading (`script_category: prize_lottery`, `requested_data: [card_number, otp]`) is weight 0 by design; (d) no `message.script_match` evidence appeared in any check.
- Size, offline, on the 160-item synthetic batch `qwen-msg-auto-20261123T032820` (local-model output, **not supervisor-audited**, text rules only): 7 of 96 scam messages flagged, 0 of 64 legitimate ones.
- Also: there is no published eval of message-text detection. `evals/harness/message_path.py` wraps URL items in four templates, so its recall is the URL model's recall. `test.message_path.dangerous_recall` in the published artifact is 0.0.
- Fix: PR #75 covers (a). The rest is a hand-off (H1 below).

### P1

**F4. Operations cannot see a failure.** Evidence from the main stack's Prometheus.
- No alert fired while the Sentinel was down for over an hour. Every Sentinel alert reads a gauge the Sentinel exports.
- `fl_feed_age_seconds` and `fl_feed_enabled` return no series, while the API reports `feed_age_s: 39534, fresh: false`. They are declared on a registry no service renders (`signals/reputation/metrics.py`), so `FeedStale` can never fire.
- The one alert firing is `RouteAgreementDrop`, with shadow mode off: the gauge exports 0 before any sample.
- `make demo` reports an unhealthy Sentinel as SKIPPED and exits 0 (`scripts/falcon_demo/scenarios.py`).
- Fix: PRs #76 and #78.

**F5. Personal data in a checked link is stored and returned.**
- Evidence: checking `http://falcon-demo-bank.test/reset?email=‹invented›&phone=‹invented›&token=abc123#frag` returned `canonical_url` with the email, the phone number and the fragment. `GET /v1/verdicts/{id}` returned a stored verdict with status 200 and no key.
- Impact: contradicts `docs/PRIVACY.md` ("what a person pastes is not stored as such").
- Fix: PR #81. Not covered there: URLs inside evidence details; rows already stored.

**F6. Real websites are flagged too often, from one cause.**
- Evidence, `fp_regress/a2f083cf1a77_20261123T085415Z.json`, 200 held-out legitimate domains: 57 flagged. 30 are `not_rendered:dns_failure` (bare infrastructure domains with no website), 22 are `sandbox_unavailable:timeout`, 5 are real detections to examine (`wpguardian.com` and `localytics.com` rated `dangerous`).
- So 52 of 57 false alarms are "we could not open the page", shown to the user as "suspicious". Examples that timed out: `malwarebytes.com`, `check24.de`, `gitlab.io`, `webflow.io`.
- Impact: a committee member who tries a slow, well-known site has a real chance of seeing a warning.
- Owner: the sandbox-tuning builder holds the time and size limits. The policy itself is hand-off H2.

**F7. A donation or search form is read as a credential form.**
- Evidence: live check of `https://www.wikipedia.org/` → `page.cred_form` (+1.5) with `field_kinds: ["otp"]`. Reproduced offline: the donation radio labelled "One time" matches the OTP phrase list; `<select>` is sent as type `text`.
- Impact: `page.cred_form` is half of H1 and feeds H4, so a page that names a brand and has such a form can be floored to `dangerous`.
- Fix: PR #74.

**F8. Scenario 1 (feed hit, answered at T0) depends on poll timing that the feed's terms limit.**
- Evidence: mirror last written 04:01, 11 h old at audit time; H2 needs under 6 h (`mirror.py:35`); the collector may poll every 12 h and refuses earlier polls; no `collect_loop` process is running.
- Impact: H2 is off for at least half of every cycle, and on the day the "refresh the mirror" fallback in `docs/DEMO.md` can be refused.
- Owner: **L1/owner**: schedule one poll within 6 h before the recording. Whether the freshness window should match the feed's cadence is a scoring decision (Opus).

### P2

- **F9. Stale wording on the live site and in `STATUS.md`** (see scorecard 1). Owner: the web v2 and submission builders. #66 fails `lint`; #65 has no CI run yet.
- **F10. PR #45 (DSPy)** is an offline pipeline. `falcon_core.prompts.compiled.load` is not called by the router or the Sentinel, the cloud run was not done, and the classifier's 1.0 is on a template set the PR itself calls a ceiling check. No page or document claims DSPy today (checked `README.md`, `web/lib`, both v2 branches). Keep it that way unless it is wired and measured: it must not appear under "tools used" otherwise.
- **F11. Offline and live numbers answer different questions.** The 3.75% test false-alarm rate is T1 + arbiter on 80 legitimate URLs; the 28.5% is the shipped stack. v2 part A adds the live figure to the results page (`web/lib/fp-regress.ts`); it should land before submission so the two are shown together.
- **F12. T0 p95 of 3.8 s** on the live stack. Likely a cold first lookup; not investigated.
- **F13. Safe Browsing and URLhaus are disabled** (no keys). Stated in `STATUS.md`; the evidence list shows `feed_disabled` on every check. Zero-day claims rest on H1 and H4 alone, which the fixtures do demonstrate.
