## Findings

### Blocking

1. **B1: the sentinel proxy omits `X-Operator-Key` on GETs, so every read route breaks against merged PR #6.**
   - Where: `services/api/src/falcon_api/intel.py:51-59`. `incidents()` and `incident()` send no header; only `decide()` does (`intel.py:66`). Main's sentinel requires the key on `GET /internal/incidents*` (DECISIONS on main: "/internal/incidents* all need X-Operator-Key").
   - Result: the probe got 502 on `/v1/incidents`, `/v1/campaigns`, `/v1/incidents/{id}` and `/v1/intel/stix`.
   - Silent knock-on failures:
     - The SSE streams swallow the `Problem` and emit nothing (`integration.py:252`).
     - `load_card` falls back to the raw board card (`app.py:236`), so webhooks send a non-campaign payload that doesn't match `campaign.schema.json`.
   - The tests hide it: `fake_sentinel` in `services/api/tests/test_integration.py:47-56` and `services/mcp/tests/test_mcp.py:57-69` doesn't check the header on GETs.
   - Fix:
     - Set `X-Operator-Key` as a default client header.
     - Make both fake sentinels return 401 without the header.
     - On approve/reject, send `X-Operator-Name: api:<key_id>` so the sentinel's `approved_by` identifies which API key decided. Today every API approval is attributed to the same anonymous operator.

2. **B2: SSE streams have no concurrency cap per key or per IP.**
   - Where: `integration.py:228-259`. Each stream runs for up to `STREAM_MAX_S=300` and does a blocking `XREAD` every second.
   - The Redis client is `aioredis.from_url(...)` with no `max_connections` (`app.py:199`), so each concurrent stream holds its own Redis connection.
   - Each stream also calls the sentinel once per board card, so N streams turn one card into N sentinel GETs.
   - The per-key minute limit only counts stream *opens*. With the public sandbox key (30/min x 300 s), one key can hold about 150 streams, and the probe opened 25 at once.
   - Fix:
     - Add a per-key and per-IP concurrent-stream cap (e.g. 3 per key and 3 per IP, Redis-counted with a TTL so replicas share it). Return 429 problem+json with `Retry-After` when the cap is hit.
     - Bound the Redis pool.
     - Preferably run one shared board reader per process that fans out to subscribers, instead of one `XREAD` plus one sentinel fetch per stream.
     - Add a test that the (cap+1)th stream gets 429.

3. **B3: the public sandbox key has `read`, so anyone can read full incidents, including operator-only drafts.**
   - Where: `app.py:183` seeds `sandbox` with `["check","read"]`. `.env.example` calls it the "public sandbox key for judges", and the compose default is the known `fl_sandbox_demo_key`.
   - `GET /v1/incidents[/{id}]` and `/v1/incidents/stream` return the sentinel incident verbatim (`integration.py:304-329`). That includes `actions[].draft` (`body_ar` / `body_en` of draft police reports and takedowns), `actions[].args` and `approved_by`.
   - MCP `get_incident` passes the same document through (`services/mcp/src/falcon_mcp/server.py:128-131`).
   - Fix, either of:
     - (a) A public projection for non-`operator` keys: drop `actions[].draft`, `args` and `approved_by`, and keep tool/mode/status only.
     - (b) Take `read` off the sandbox key and add a narrower scope for the campaign board.
   - Add a test that a `read`-only key never sees `draft`.

4. **B4: the default operator secret is now a public, full-scope API key.**
   - Where: `app.py:184` seeds `FL_OPERATOR_KEY` as an API key with `check, read, operator, intel`, reachable through the public gateway.
   - `docker-compose.yml` defaults it to `change-me-operator`, and nothing refuses that value. Before this PR, the key only guarded sentinel routes on the internal network.
   - On a demo or tunnel deploy left at defaults, anyone can approve or reject held actions and export intel. The same secret also doubles as the sentinel's internal credential.
   - Fix:
     - Refuse to seed any configured key that starts with `change-me` or is shorter than 24 chars when `FL_ENV != local`; log it and skip it. The same rule applies to `FL_MCP_SERVICE_KEY` and `FL_MCP_BEARER_TOKEN`.
     - Preferably give operator API access its own key, separate from the sentinel's internal `FL_OPERATOR_KEY`.
     - Add tests.

5. **B5: STIX `pattern` refangs indicators, which breaks CONTRACTS invariant 5 ("URLs in any output are defanged"). The refang is also incomplete.**
   - Where: `intel.py:195` (fallback) and main's `falcon_core/tools/stix.py` `_pattern` both replace only `[.]`.
   - Result: domains come out live (`falcon-demo-1.test`), while URLs come out as `hxxps://falcon-demo-1.test/login`, which is neither defanged nor a valid STIX `url:value`. The test locks this in: `test_integration.py:257` "refanged for the STIX pattern".
   - A machine-readable IOC feed arguably needs real values, but that needs an L1-recorded exception.
   - **Escalated to L1:**
     - either keep patterns defanged,
     - or record in `docs/CONTRACTS.md` that STIX patterns behind the `intel` scope carry refanged values, and then refang fully (`hxxp` back to `http`) in one shared helper.
   - Whichever L1 chooses, delete the local `_fallback_bundle` after the rebase, as DECISIONS already says, so only one builder exists.

6. **B6: rebase onto main and get CI green.** `uv.lock` conflicts with main and `gh pr checks 30` reports no checks, so CI has never run on this PR. Approval needs a green CI run on the rebased head, with the openapi drift check, the contracts job and `make guard`.

### Non-blocking (fix in this PR if cheap)

7. **Audit-log immutability is not verified on Postgres, and the docs overclaim it.**
   - Where: `db.py:32-40`.
   - The triggers are the right idea, but `REVOKE ... FROM PUBLIC` does nothing against the owning app role. That role can also `DROP TRIGGER`, and the DDL does exactly that on every start.
   - `test_audit_log_is_append_only` (`test_integration.py:156`) only checks a Python class. `docs/INTEGRATION.md:16` says "`UPDATE`, `DELETE` and `TRUNCATE` are revoked and blocked by triggers".
   - Fix:
     - Reword to "blocked by triggers; the owning role can still drop them".
     - Add a Postgres-backed test (CI service container) that UPDATE, DELETE and TRUNCATE raise.
     - Longer term, use a separate audit-writer role without ownership.

8. **Webhook replay inside the window.**
   - `verify()` (`webhooks.py:41-51`) and `verify_webhook` accept the same delivery repeatedly for 300 s.
   - Fix: tell receivers in `docs/INTEGRATION.md:27` to de-duplicate on `X-Falcon-Delivery` (or body `id`), and offer an optional `seen` callback in the client.
   - Also, when the sentinel is unreachable, `load_card` (`app.py:236`) should skip or retry the delivery rather than send a non-campaign card.

9. **Invalid-key requests are not rate-limited, and each one writes an audit row.** See `app.py` guards, the `principal is None` branch. This lets an attacker amplify Postgres writes. Fix: add a per-IP limit on 401s.

10. **Negative-cache flush lets random keys evict valid principals.** `auth.py:150-152` clears the whole cache at 4096 entries. Fix: cache only positive results, or use an LRU.

11. **`campaign.schema.json` vs code.**
    - `count` is described as "Number of linked domains/URLs", but the code uses `max(len(inds), len(linked_verdicts))` (`intel.py:150`).
    - `source` defaults to `"live"` when the incident lacks it (`intel.py:157`). That can mislabel replayed or synthetic data. Use the incident's value or fail.

12. **Docs gaps.** `docs/CONTRACTS.md` lists `campaign.schema.json` but does not mention the optional `timeline[].what_ar` / `what_en` additions to `incident.schema.json`. Add one line, and note that the sentinel on main does not emit them yet.

13. **MCP annotations.** `check_url`, `check_message` and `check_email` are annotated `read_only_hint=True` (`server.py:72-96`), but they create verdict jobs and stored records. Use a non-read-only, non-destructive annotation.

## Confirmed OK

  - Lookup is by HMAC fingerprint, and argon2 runs only for real keys, so there is no timing or enumeration signal.
  - A presented-but-wrong key gives 401, never silent anonymous access.
  - Scope checks run on approve, reject and stix, plus a `check` scope gate on `/v1/check/*`.
- **Reports:** raw text is stored only with `consent_store_text`, and events carry hashes only (test plus probe).
- **MCP:**
  - The bearer uses a constant-time compare and fails closed when unset.
  - DNS-rebinding allow-list and Origin checks hold.
  - `screenshot_url` is stripped from verdicts.
  - The service key has `check`+`read` only, so there is no approve or STIX path.
- **Errors:** problem+json bodies do not echo submitted values (except the inherited `instance` path; see the probe results).
- **Docs:** `INTEGRATION.md` heading reads "ready to connect (not connected)" and states there is no ADP integration or endorsement. No "safe" verdict wording. No hand-typed metrics. `/v1/meta` thresholds come from `params.yaml` (draft), not literals.
- **Repo hygiene:** no live phishing URLs or logos in committed files, and gitleaks is clean.
