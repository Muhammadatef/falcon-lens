## Proxy attack results (`scratchpad/probes/pr16_proxy.py`)
- **Host smuggling.** `GET http://public.example.com/` with `Host: 169.254.169.254` and a second `host: inside`: both client Host headers are dropped. The upstream saw only `Host: public.example.com`, and the proxy dialled `93.184.215.14:80`.
- **Absolute-form with userinfo.** `http://public.example.com@127.0.0.1/` and `http://u:p@public.example.com/` → 403 `userinfo`. `http://public.example.com\@127.0.0.1/` → 403 `invalid_url`. `#@127.0.0.1` → the host is `public.example.com`, which matches WHATWG. `%31%32%37.0.0.1` → `obfuscated_ip`.
- **CONNECT to a name that resolves to an internal address.** private → `private`, metadata → `metadata`, mixed `[public, 127.0.0.1]` → `loopback` (every record is checked), AAAA `::1` → `loopback`. `[::1]` → `loopback`, `localhost.` → `internal_name`, `0x7f000001` → `obfuscated_ip`, port 22 → `port`. A fixture host that is allow-listed but resolves to metadata → `metadata`. Nothing was dialled in any of these cases.
- **Request smuggling.** Duplicate `Content-Length: 0` + `Content-Length: 5`, `Content-Length: 0, 5`, `Transfer-Encoding: chunked`, `Transfer-Encoding : chunked`, obs-fold, bare LF inside a header and NUL inside a header → all 400 with nothing dialled. Bare LF or TAB in the request target → 403 `invalid_url`. A pipelined second request to `inside.example.com` is never forwarded; the upstream saw exactly one request with `Connection: close`.
- **Oversized headers.** 9 KB → 431. 40 KB, which is over the stream limit and hits `LimitOverrunError`, → 431.
- **Other refusals.** POST → 405, absolute-form https → 403 `scheme`, `:8080` → 403 `port`, origin-form → 400, `HTTP/2.0` → 400.

### Non-blocking (for a follow-up card)
1. **LOW** `packages/falcon_core/src/falcon_core/security/ssrf.py:387-400` (`_normalise_host_port`, used by CONNECT). The authority goes through `httpx.URL(f"http://{h}/")`, so userinfo and paths are dropped silently. `CONNECT a@public.example.com:443` → **200 Connection Established**, and the log says `"host": "a@public.example.com"`. `public.example.com@inside.example.com` → the resolver is asked for `inside.example.com`. This is **not a bypass**: the IP that gets dialled is always the one checked for the normalised host, and `a@0x08080808`, `a@localhost` and `x@[::1]` are still blocked. But it breaks the DECISIONS rule "Userinfo is always blocked", and the logs and metrics show the wrong host. *Fix:* reject `@ / ? # \` and whitespace in a CONNECT authority before parsing (→ `userinfo` or `invalid_url`), and add those cases to `test_connect_denied`.
2. **LOW** `services/egress/src/falcon_egress/main.py:193-204`. Headers named by `Connection:` aren't stripped. With `Connection: keep-alive, X-Foo` and `X-Foo: y`, `X-Foo: y` still reaches the upstream (RFC 9110 §7.6.1). It has no security effect because the upstream connection is `Connection: close` and one request only. Drop those headers anyway for correctness.
3. **INFO** `services/egress/tests/netcheck/probe.py`. `CONNECT redis:6379` is refused only because of `port`. Add `CONNECT redis:443` (internal name) and `CONNECT egress-proxy:443`, so the container-level test proves the name and private-IP checks too, not just the port allow-list.
4. **INFO** In proxy mode, an origin can return its own `403` with `X-Falcon-Block-Reason` (the PR's residual-risk list covers this). With PR #18 that turns into a degraded `suspicious`, so it fails toward caution. That's acceptable. Note it on the sandbox card.
5. **INFO** `CONNECT host:0443` is accepted as port 443. That's harmless.
