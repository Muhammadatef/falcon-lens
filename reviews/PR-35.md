The new `web` CI job has therefore never run on GitHub. `git merge-tree --write-tree HEAD origin/main` shows:
   - `CONFLICT (content): Merge conflict in Makefile`. Keep main's `DEMO=` variable, the `unblock` target and the G6 demo targets (`seed`/`replay`/`demo`/`urls`/`tunnel`/`tunnel-stop`/`demo-reset`). Add `test-web` to `.PHONY`, `help` and the target list.
   - `CONFLICT (content): Merge conflict in infra/gateway/Caddyfile`. Keep #21 exactly:
     - `trusted_proxies static private_ranges` and `client_ip_headers Cf-Connecting-Ip X-Forwarded-For` in the global `servers {}` block.
     - `reverse_proxy api:8000 { header_up X-Forwarded-For {client_ip} }` in `handle /v1/*`.

     Then add this PR's per-handle `header Content-Security-Policy "default-src 'none'; frame-ancestors 'none'"` lines and remove the site-wide CSP line.

   Merge or rebase onto main, push, and wait for all CI jobs (including `web`) to pass.

2. **`/share` checks all land in one rate-limit bucket (the tunnel's).** The problem is the web handle (`infra/gateway/Caddyfile`, the bare `handle { reverse_proxy web:3000 }`).
   - `web/app/share/route.ts:21-22,73` forwards the incoming `X-Forwarded-For` to `api:8000`.
   - The API's `client_ip()` (`services/api/src/falcon_api/app.py:83-95` on main) trusts the last XFF hop from a private peer.
   - #21 added `header_up X-Forwarded-For {client_ip}` only on `/v1/*`. On the web handle, Caddy keeps the client-supplied XFF and appends its own peer address, which is cloudflared's.

   I reproduced this with a throwaway `caddy:2.11.9-alpine` that uses the same `servers` options, sending `Cf-Connecting-Ip: 203.0.113.7` and `X-Forwarded-For: 198.51.100.9`:
   ```
   web:  xff=198.51.100.9, 127.0.0.1     <- last hop = proxy peer, not the visitor
   v1:   xff=203.0.113.7                 <- correct (#21)
   ```
   Behind the tunnel, every share-target check from every visitor therefore counts against cloudflared's IP. One person sharing in a loop can rate-limit sharing for everyone, which is the same failure #21 fixed for `/v1`.

   **Fix:** use `handle { reverse_proxy web:3000 { header_up X-Forwarded-For {client_ip} } }`. The share route then forwards a single trusted value. Add a line to the live test or the mock gateway asserting that the API sees the visitor's address on `/share`.

3. **Contract invariant 4 is not enforced in the client: a degraded verdict could be shown as "no warning signs".**
   - `web/lib/contracts.ts:188-252` (`parseVerdict`) accepts `degraded: true` together with `verdict: "no_warning_signs"`.
   - `web/components/Result.tsx:173-190` then renders the plate «لم نجد علامات تحذير» with the degraded note under it.
   - `tests/unit/contracts.test.ts:42` checks the invariant only on our own fixtures, not on the parser's output.

   The owner rule is that degraded is never shown as no_warning_signs, and the UI must not rely on the API alone for that. **Fix:** in `parseVerdict`, map degraded `no_warning_signs` to `suspicious`, or reject it. Do the same for a `no_warning_signs` verdict with no `actions.caution`: make sure the "Stay careful" block still renders, for example from a default caution list. Add unit tests that feed both malformed payloads through `parseVerdict` and through the e2e mock.

## Non-blocking (fix now or file as P2)

4. `web/proxy.ts:45-55` excludes `fonts|icons|sw.js|_next/static|api` from the matcher. Since the gateway no longer sets a CSP on web routes, any HTML that Next serves under those paths (for example a 404 page for `/_next/static/x`) goes out with no CSP at all. Suggest a Caddy fallback on the web handle, `header ?Content-Security-Policy "default-src 'none'; frame-ancestors 'none'"` (sets the header only when the upstream did not), which keeps "exactly one CSP". Also, `(?!api|…)` skips every path that merely starts with `api` (for example `/apis`). Use `api/`.
5. `web/app/share/route.ts` `POST` has no `Origin`/`Sec-Fetch-Site` check, so any website can make a visitor's browser start a check. The impact is low (anonymous checks, rate-limited once item 2 is fixed). Consider refusing `Sec-Fetch-Site: cross-site`, but test it on Android share first.
6. The live project (`tests/live/gateway.live.ts`) was **not** run. The running `falcon` stack on 8443 serves main's web and Caddyfile, not this PR's: `curl -skI https://localhost:8443/` still returns the old `script-src 'self' 'unsafe-inline'` policy. Running it there would test main, not this PR. It must pass on the rebuilt stack after merge, and I will run it on a fresh clone as part of the gate.
7. `make scan`: `syft` is not installed locally, so the SBOM step was skipped (a tooling gap, not a PR defect).
